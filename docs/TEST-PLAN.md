# 1C-telemetry — согласованный план реальных испытаний v1

Статус: архитектура стенда согласована, сервер ещё не установлен, E2E NOT_RUN. Поставка заказчику — два полных ZIP XML/BSL, примеры и инструкции. CFE не выдаётся заказчику. Имена внутренних серверов, URL, секреты, данные и пути находятся вне публичного репозитория.

## Стенд и ответственность

- Сервер: имеющаяся тестовая ИБ 1С:Предприятие 8.3.27.2342, администратор устанавливает серверное расширение из точно того ZIP, который проходит приёмку, и отдельно публикует его HTTP-сервис через существующий Apache/HTTPS. Сохраняются прежние публикации и настройки. Производственная ИБ не участвует.
- Отправитель: разрешённая Windows-станция с удалённым доступом; разработчик выполняет PowerShell, Python (при наличии) и curl.exe. Тесты не требуют наличия 1С на станции для проверки сервера.
- Контроль: доступный личный MCP тестовой ИБ, чтение только объектов ТЛМ_* после discovery метаданных, с фильтрами по специально выделенным тестовым клиентам и идентификаторам. Если MCP не позволяет прочитать регистры — штатный список/выгрузка администратора. MCP не участвует в самом транспорте и не является зависимостью продукта.
- Для проверки клиентского расширения требуется исполнение BSL в разрешённой тестовой ИБ. Предпочтительна отдельная неопубликованная файловая ИБ; если её пока нет, временная проверка клиентского модуля на той же тестовой ИБ допустима с отдельным токеном и явно выделенными данными, но не доказывает автономную неопубликованную файловую 1С. При отсутствии доступа к исполнению администратор запускает предоставленный BSL-образец и регламентное задание. Не создавать базы, не менять ОС/публикацию или запускать тяжёлые тесты без согласования.

## Однократная подготовка владельцем

1. Backup тестовой ИБ, распаковка ZIP сервера и импорт в расширение, CheckConfig, обновление ИБ; зафиксировать версию/SHA-256. Включить только наш HTTP-сервис в существующей публикации или выделить отдельную, не нарушая текущие сервисы.
2. Задать ТЛМ_Сервер_КаталогФайлов, лимит JSON, создать каталог вне web root с правом записи процесса исполнения 1С; проверить свободное место. Создать минимум два тестовых клиента со своими токенами. Передать тестовый HTTPS URL сервиса, секреты и при необходимости публичный PEM по закрытому каналу (не GitHub).
3. Для проверки хеша физического файла обеспечить узко ограниченное чтение тестового каталога либо выполнение штатного хеширования владельцем на сервере. Запрос регистра сам по себе не доказывает совпадение физических байтов.
4. Установить клиентский ZIP в согласованную тестовую ИБ, CheckConfig; заполнить настройки, доступ к тестовому файлу на машине исполнения и при необходимости доверие к сертификату. Предоставить способ запуска тестового BSL/штатного задания.

## Протокол тестов

| ID | Действие | Доказательство PASS |
|---|---|---|
| T01 | XML/BSL preflight, BSL LS, native syntax, ZIP roundtrip и комментарии/copyright | точный SHA, отчёты, версии инструментов; учебная платформа отдельно |
| T02 | Штатный импорт серверного и клиентского ZIP, CheckConfig | реальные логи платформы, версии, отсутствие конфликтов с основной конфигурацией |
| T03 | GET ping, доверенный TLS и X-Token | 200 + ok; отсутствие записи в истории |
| T04 | POST json с кириллицей, массивом, переносами, пробелами | 201 + id; точный readback исходного текста, клиент и дата совпадают |
| T05 | POST file с TXT, пустым файлом, кириллическим именем и двоичными данными | 201 + id; запись в регистре, исходное имя, размер, путь и SHA-256 физического файла совпадают |
| T06 | Повтор, одинаковые имена, параллельные отправки двух токенов | независимые записи и файлы без перезаписи и смешения клиентов |
| T07 | Отсутствующий/неверный/отозванный токен, неверный сертификат/SAN, redirect, превышение JSON-лимита | отказ, без нарушений ACL/регистрации и утечки токена; negative TLS на безопасном fixture, не замена действующего сертификата |
| T08 | Сбой чтения, записи, связи и некорректное имя файла | корректный HTTP/BSL результат; локальные/сетевые сценарии без остановки общего сервиса; не заполнять общий диск |
| T09 | Прямая передача 1, 10, 100, 500 МиБ, 1, 2 и 3 ГиБ (последовательно при достаточных ресурсах) | HTTP, SHA-256, время, пик RAM при доступности метрик, фактический предел; прекращать при риске для тестовой ИБ; без блочного протокола |
| T10 | Отдельный вызов всех трёх функций BSL, позитивные и отрицательные результаты | общая структура из шести полей, реальные записи; скрипты не заменяют BSL |
| T11 | Собственное штатное регламентное задание из клиентской базы | минимум три фактические записи по заданному расписанию, фиксировать режим ИБ и активность исполнителя |
| T12 | Обновление/повторное испытание | неизменность прежней истории, актуальные ZIP и хеши, повторный smoke/negative; первая версия — upgrade NOT_RUN |

Для каждого запроса использовать синтетические данные, уникальные ID/имена и безопасный временный каталог. Сначала небольшие запросы, затем большой файл только при проверенных ресурсах и разрешении владельца; не останавливать общие службы, не менять TLS/ACL действующего окружения ради негативного теста. При невозможности безопасного fault injection — NOT_RUN, отдельно описать. Чистку только тестовых файлов/записей осуществляет администратор по согласованию, не добавлять автоочистку в продукт.

## Выпуск
Документировать отдельно SOURCE_CHECK, NATIVE_SYNTAX, CHECKCONFIG, SERVER_HTTP_E2E, FILE_READBACK, CLIENT_BSL_E2E, SCHEDULE_E2E, LARGE_FILE_LIMIT, UPGRADE. Для каждого PASS/FAIL/NOT_RUN с точным SHA, датой, версией платформы, фактическим результатом и ограничениями; при недоступности платформы или данных не присваивать PASS. Перед stable release оба расширения должны пройти функциональную приёмку; при выдаче промежуточного ZIP для установки — TEST, честные статусы. Публиковать только обезличенный протокол, манифесты и неизменяемые ссылки; не раскрывать секреты или инфраструктуру.
