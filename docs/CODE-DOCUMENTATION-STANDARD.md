# Обязательный стандарт BSL и документирования кода

Применяется ко всему production BSL, Python, PowerShell, Shell, XML, тестовым и сборочным скриптам. Политика адаптирована из OFFICE20 CODE-DOCUMENTATION-STANDARD (25.09.2026).

## Авторские блоки
В начале и конце каждого файла, где синтаксис допускает комментарии, указать проект, назначение модуля и Copyright © 2026 Тарасов Роман Олегович. Все права защищены. Для Python/shell — после shebang/encoding; XML после declaration, если штатная выгрузка 1С допускает; иначе штатные свойства Comment/Copyright. Для JSON не нарушать схему: фиксировать авторство в ближайшей документации. Для обоих расширений обязательны Comment с названием проекта и copyright и заполненное штатное поле Copyright. Сторонние уведомления сохранять.

Пример шапки BSL:
    // ============================================================================
    // 1C-telemetry
    // Общий модуль: ТЛМ_Клиент
    // Назначение модуля: отправка готовых данных по HTTPS.
    // Copyright © 2026 Тарасов Роман Олегович. Все права защищены.
    // ============================================================================
Конец модуля — аналогичный блок с именем и копирайтом.

## Комментарии и оформление
Русский человеческий технический язык. Перед каждой функцией/процедурой/методом/классом объяснить назначение и зачем нужен, параметры/типы, результат, побочные эффекты, ошибки и обязательные предположения. Пояснить ключевые переменные, пути, идентификаторы, сроки, настройки, секреты, хеши и состояние; не писать механические комментарии каждой очевидной строки. При существенной правке весь затронутый модуль привести к стандарту. Из кода должно быть понятно, как сопровождать его без чата. Короткие читаемые процедуры, осмысленные русские имена BSL, единое форматирование, отступы, разделы модулей, без мёртвого кода/пустых заглушек/привилегированных и глобальных серверных общих модулей. Не ломать стандартную кодировку выгрузки 1С; проверять UTF-8 и кириллицу. Стабильные UUID объектов метаданных.

Security/auth/FS/network/release: описать актив, угрозу, trust boundary, почему выбран механизм, fail-closed, ограничения, запрет секретов в логах, отзыв/rollback и проверку. Не использовать непроверенные методы BSL или предположения о контексте; проверить Syntax Assistant/помощь и нативный компилятор.

## Проверки
- XML: парсинг, обязательные свойства и дочерние пути, роли/HTTP маршруты, уникальность UUID, соответствие Configuration.xml/ConfigDumpInfo (если формат выгрузки их требует), отсутствие ссылок на основную конфигурацию и собственных форм.
- Лексический preflight BSL: пары Функция/КонецФункции, Процедура/КонецПроцедуры (включая Асинх), строки/комментарии и ошибочные обратные слеши вне строк; он не является полной грамматикой. Не копировать пороги количества модулей OFFICE20 — инвентарь определяется реальным деревом.
- BSL Language Server: зафиксировать версию/настройки, запустить для каждого модуля; исправить ошибки/критические диагностики, обоснованные исключения документировать, не отключать диагностику ради PASS.
- Использовать доступные 1С help, BSL reference/static/платформенную проверку; затем штатный CheckConfig/проверку модулей в целевой платформе, импорт/установку и HTTP E2E. Проверять клиентский/серверный контексты. Отдельно указывать NOT_RUN.
- Автоматические guards комментариев/copyright, синтаксиса, метаданных, версий и упаковки включить до первого релиза. Unit/negative тесты; не считать число определённых тестов числом выполненных. Сохранить точный SHA/вывод/версию инструмента; без реальных данных.
