# Установка и эксплуатация

Скачайте комплект **TEST 1.0.3-dev** с [главной страницы](../README.md). Для каждой базы нужен свой резервный снимок. Целевой стенд первой установки — 1С:Предприятие 8.3.27.2342 и отдельная HTTPS-публикация Apache. Фактические результаты записаны в [отчёте приёмки](ACCEPTANCE.md).

## 1. Установка сервера

1. Сверьте ZIP с опубликованным SHA-256. Например, в PowerShell: `Get-FileHash -Algorithm SHA256 .\имя.zip`.
2. Распакуйте серверный ZIP в пустой каталог. Файл `Configuration.xml` находится в его корне. В Конфигураторе выполните **Конфигурация → Расширения конфигурации**, создайте дополнение `ТЛМ_Сервер`, откройте его и загрузите конфигурацию из файлов. Выполните штатную проверку конфигурации (CheckConfig), сохраните её и обновите конфигурацию базы данных для расширения. Зафиксируйте подробный лог.
   Комплект поставки использует заимствованный основной язык Русский и режим интерфейса «Такси и версия 8.2». Если целевая конфигурация использует другой профиль, согласуйте контролируемые свойства в Конфигураторе.
   После ошибки обновления SDBL о длине дескриптора в версии 1.0.2-dev загрузите исходники версии 1.0.3-dev в то же дополнение. Повторите обновление конфигурации базы данных.
   При ошибке XDTO `Copyright` на первом ZIP используйте чистую распаковку версии 1.0.3-dev. Для теста можно повторно загрузить файлы в ранее созданное пустое дополнение.
3. Создайте выделенный каталог вне корня сайта и вне каталога загрузки чужих файлов. Разрешите его чтение, создание, перемещение и удаление файлов только учётной записи процесса исполнения 1С и системному администратору. Настройте для расширения разрешённые операции в штатном профиле безопасности, где он применим. Проверьте реальное исполнение безопасного режима в вашей схеме. Каталог должен быть локальным абсолютным путём ОС, например `D:\Telemetry` или `/var/lib/telemetry`. Корень и его родители должны находиться под контролем администратора, без символических ссылок и junction в пути. В многосерверном кластере направляйте обработку в один и тот же защищённый каталог или выделите узел исполнения.
4. Назначьте `ТЛМ_АдминистраторСервера` оператору настроек. Отдельному техническому пользователю публикации назначьте `ТЛМ_ПриемТелеметрии`. У него есть программное чтение справочника клиентов и чтение/обновление двух регистров. Это права платформы, необходимые для записи. Ограничение до добавления новых записей обеспечивается кодом обработчиков и границей выделенной публикации. Уберите прикладные роли, доступ к UI, администрирование, выполнение произвольного кода. Сверьте фактически действующие права и права по умолчанию базовой конфигурации.
5. В своём административном серверном BSL задайте `ТЛМ_Сервер_КаталогФайлов` и при необходимости `ТЛМ_Сервер_МаксимальныйРазмерJSONМБ`. Значение 0 применяет лимит 10 МиБ, положительное число задаёт лимит в МиБ, отрицательное отключает приём JSON до исправления. Ping и приём JSON независимы от настройки каталога. Готовые примеры находятся в [НастройкаСервера.bsl](../examples/bsl/НастройкаСервера.bsl).

### Регистрация токена

Один элемент справочника `ТЛМ_Клиенты` на базу или скрипт. Сформируйте 32 байта криптографическим генератором ОС и запишите как 64 строчных шестнадцатеричных символа. Подходит `python -c "import secrets; print(secrets.token_hex(32))"` в закрытом сеансе. Установите секрет через административный BSL:

```bsl
Итог = ТЛМ_Сервер.СгенерироватьТокен(СсылкаКлиента, СекретИзЗакрытойНастройки);
```

Выдача и ротация принимают готовый секрет. В справочнике сохраняется SHA-256; действующий токен после фиксации известен только оператору и получателю секрета. Для ротации вызовите метод с новым секретом. Для отзыва вызовите `ТЛМ_Сервер.ЗаблокироватьКлиента(СсылкаКлиента)`. Уже принятые запросы могут закончить запись. Сохраняйте историю и связи с клиентом. Полученный статус или структуру целиком в журнал не выводите.

### Отдельная HTTPS-публикация

В существующей тестовой публикации добавьте только запись сервиса в её `default.vrd`. Сохраните строку подключения `ib`, настройки остальных сервисов и резервную копию за пределами веб-каталога. Сравните ответы контрольных маршрутов до и после правки. Используйте действующий сертификат и доступ только по HTTPS. В `default.vrd` проверьте публикацию `ТЛМ_ПриемДанных` с корнем `telemetry`. Для существующего блока добавьте только строку `<service …/>`. При создании блока можно использовать этот профиль:

```xml
<httpServices publishByDefault="false" publishExtensionsByDefault="false">
    <service name="ТЛМ_ПриемДанных" rootUrl="telemetry" enable="true"/>
</httpServices>
```

Для отдельной публикации можно выбрать техническую учётную запись 1С. При добавлении сервиса в существующую публикацию сохраняется её схема аутентификации. Если для этого используется `Usr` / `Pwd` в строке подключения `ib`, защищайте дескриптор ACL ОС и от выдачи по HTTP. Apache/IIS должны пропускать только `/central/hs/telemetry/{ping,json,file}` к этой публикации. Отключите клиентский доступ, OData, SOAP, переадресацию и автопубликацию чужих сервисов. Если платформа требует включить сервисы расширений по умолчанию даже при точечной настройке, сначала ограничьте вход по маршрутам на веб-сервере. Сверьте [руководство 1С:Предприятие 8.3.27](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/) для установленной версии.

С отправителя проверьте `GET /central/hs/telemetry/ping`: без заголовка ожидается JSON `401 invalid_token`, с токеном — JSON `200`. Ответ Basic challenge или запрос пароля означает, что запрос ещё не дошёл до обработчика. С тем же способом доступа проверьте, что URL веб-клиента и других сервисов закрыты.

## 2. Установка клиента

В клиентской ИБ аналогично загрузите клиентский ZIP в отдельное дополнение `ТЛМ_Клиент`. Публикация этой ИБ не нужна. Назначьте `ТЛМ_АдминистраторКлиента` тому, кто задаёт настройки, и `ТЛМ_ОтправкаТелеметрии` — исполнителю серверного BSL или задания. Доступ к чтению токена равнозначен доступу к отправке. Роль исполнителя выдавайте только доверенной учётной записи.

| Константа | Значение |
|---|---|
| `ТЛМ_Клиент_АдресСервера` | Например `https://server.example/central/hs/telemetry/`. Допустим нестандартный порт и вложенный путь. |
| `ТЛМ_Клиент_Токен` | Отдельный секрет этого отправителя. |
| `ТЛМ_Клиент_ПутьКСертификату` | Путь к публичному PEM или пустая строка для доверия ОС. |
| `ТЛМ_Клиент_Таймаут` | Целые секунды. 0 применяет 60, отрицательные значения отклоняются. |

Файл и PEM должны быть доступны на машине, которая исполняет серверный BSL. В серверном режиме это рабочий процесс 1С, в файловом — исполняющий сеанс. Проверьте исходящий HTTPS и чтение только нужных путей. Пример настройки и вызовов в [НастройкаКлиента.bsl](../examples/bsl/НастройкаКлиента.bsl). В каждом расширении есть русская HTML-страница штатной справки в `Ext/Help` подсистемы справки. Проверка отображения включена в установочную приёмку.

## Сертификаты, диск и большие файлы

Для частного УЦ или самоподписанного сертификата получите публичный PEM закрытым доверенным способом и сверьте отпечаток. Администратор добавляет его в доверие ОС для нужной учётной записи либо указывает PEM в клиентской константе. В Windows PowerShell 5.1 используется доверие Windows, Python и cURL могут принять публичный PEM. SAN должен соответствовать URL: IP указывают как IP в SAN, имя — как DNS. После смены самоподписанного сертификата обновите доверие.

Один файл идёт одним POST. Контролируйте место на томе каталога и томе временных файлов веб-сервера, а также память и таймауты. У Apache проверьте [LimitRequestBody и таймауты](https://httpd.apache.org/docs/2.4/mod/core.html#limitrequestbody) для конкретной публикации. У IIS проверьте [requestFiltering / maxAllowedContentLength](https://learn.microsoft.com/iis/configuration/system.webserver/security/requestfiltering/requestlimits/). BSL использует файловое тело на отправке и поток запроса на приёме. Буферизацию транспорта Apache/1С и предел 2–3 ГиБ устанавливают измерением. При неопределённой причине ошибки записи сервер возвращает `storage_error`; ёмкость диска проверяет администратор. Подробности в [контракте ошибок](TRANSFER-AND-ERRORS.md).

## Резервное копирование и откат

Резервируйте ИБ и файловый каталог вместе в согласованной точке. Перед обновлением остановите приём в выделенной публикации, дождитесь окончания запросов, сделайте резервные копии и снимок дескриптора. Загрузите новый ZIP в существующее расширение, проверьте CheckConfig, восстановите публикацию и выполните smoke с двумя токенами. Для отката используйте согласованные копии ИБ и диска. Простое удаление серверного расширения может удалить данные его регистров.

Операции с диском и БД фиксируются отдельно. При аварии между переименованием и фиксацией возможен файл `<UUID>.bin` без строки регистра. После прерванной загрузки возможен `<UUID>.tmp`. При остановленном приёме сверяйте UUID, дату и размер с регистром. Удаление проверенных сирот и тестовых данных выполняет администратор; старые файлы, соответствующие строкам регистра, сохраняются.
