# Техническое задание v1.0 — 1C-telemetry

Статус: принятое направление проекта, все функциональные пункты до реализации NOT_IMPLEMENTED. Цель — простой универсальный транспорт JSON и файлов из любых 1С и скриптов в одну центральную 1С. Заказчик — администратор и разработчик своих задач.

## Границы
Два независимых расширения (назначение «Дополнение»), префикс ТЛМ_, без заимствованных объектов основной конфигурации, БСП, OFFICE20, Gateway, собственных форм/обработок/планировщиков/оболочек/агентов, внешней СУБД. Никакого анализа бизнес-содержимого JSON, автоматического удаления истории или исполнения файлов. Поддержка конфигураций с управляемым интерфейсом, файловых и клиент-серверных ИБ, Windows/Linux, IIS/Apache, IP/DNS, HTTPS публичного/частного УЦ и самоподписанного сертификата — целевая матрица, не заявление о проверенной совместимости. Минимальная версия и режим совместимости определяются по реальной платформенной проверке, стартовый ориентир 8.3.27.

## Клиент
Общий модуль ТЛМ_Клиент, серверное выполнение (не привилегированный и не глобальный); доступ из пользовательского серверного BSL, включая регламентные задания. Экспортные функции:
- ОтправитьJSON(JSON): готовая строка UTF-8; не преобразовывать структуру, сохранять исходный текст.
- ОтправитьФайл(ПутьКФайлу): файл доступен среде исполнения BSL (в клиент-серверной ИБ это сервер 1С); исходное имя извлекается из пути и кодируется в URL.
- ПроверитьПодключение(): GET ping проверяет TLS и токен, не пишет историю.
Единый контракт результата всех трёх функций определён в [TRANSFER-AND-ERRORS.md](TRANSFER-AND-ERRORS.md): Успех, КодОшибки, ОписаниеОшибки, КодHTTP, Идентификатор, Состояние. Штатные ошибки возвращаются структурой; неизвестный итог отличать от отказа. Без скрытых повторов обычных сообщений, очередей и заданий. ОтправитьФайл автоматически использует блоковый протокол для крупных файлов; повтор блока допустим только идемпотентно в рамках того же upload_id. Таймаут применяется к каждому запросу, не ко всему файлу.

Константы:
| Имя | Тип | Значение |
|---|---|---|
| ТЛМ_Клиент_АдресСервера | Строка | полный HTTPS URL корня сервиса |
| ТЛМ_Клиент_Токен | Строка | секрет источника |
| ТЛМ_Клиент_ПутьКСертификату | Строка | необязательный путь к публичному PEM на машине исполнения, пусто — системное доверие |
| ТЛМ_Клиент_Таймаут | Число | секунд, по умолчанию 60 |

Не создавать форм констант вручную. Заполнять стандартными средствами (при отсутствии удобного штатного интерфейса — программно через Константы в администраторском BSL). Запрет пустых адреса/токена и переадресации секрета на другой origin. HTTPS обязателен, сертификат и имя/IP проверяются. TLS-ошибку возвращать с понятной диагностикой без секретов.

Заказчик создаёт свой серверный модуль и регламентное задание в собственном расширении. В процедуре самостоятельно формирует произвольный JSON (например из выборки) и вызывает библиотеку. Настройка расписания в Конфигураторе и штатных средствах конкретной конфигурации. Для неопубликованной файловой ИБ нужен работающий исполнитель регламентных заданий; закрытая ИБ сама не запускается. Пример отдельного расширения с регламентным заданием или полный XML/BSL образец без зависимости от конкретной конфигурации; отдельно пояснить запуск в файловой/серверной ИБ.

## Сервер
- ТЛМ_ПриемДанных: единственный HTTP-сервис, RootURL telemetry, POST /json, POST /file, GET /ping; для крупных файлов дополнительно /file/init, /file/part, /file/status, /file/complete согласно API. Авторизация по X-Token. HTTPS на веб-сервере, а не внутри расширения.
- ТЛМ_Сервер: непубличный общий модуль служебной логики. Методы администратора СгенерироватьТокен(Клиент), ЗаблокироватьКлиента(Клиент); проверка токена в обработчике (служебная, не HTTP-метод). Генерация криптографически стойких 256-битных секретов штатно/проверенным источником; если нет переносимого CSPRNG, документировать генерацию администратором внешним штатным средством и регистрацию секрета, не подменять случайным UUID. Токен выдаётся при создании, в базе хранится SHA-256 высокоэнтропийного секрета, а не открытый текст. Уникальность хеша; ротация, деактивация. Технический пользователь публикации не должен иметь доступ к остальной базе.
- ТЛМ_Клиенты — справочник: Наименование, Активен, ХешТокена; уникальная ссылка. Удаление клиента не должно разрушать историю или файлы; блокировать вместо удаления.
- ТЛМ_ПолученныеJSON — независимый непериодический регистр сведений: измерения Клиент и ИдентификаторСообщения (UUID в проверенном допустимом типе), реквизит/ресурс ДатаПолучения (серверное время), JSON (строка неограниченной длины, проверить платформой). Хранить каждый принятый JSON целиком, включая пробелы, кириллицу и переносы, без десериализации/схемы/извлечения полей. Проверка транспортного UTF-8 и лимита не является разбором JSON. Администратор получает список через штатный отбор по клиенту/дате. Повторная отправка — отдельная запись; две записи в секунду не перезаписывают друг друга.
- ТЛМ_ПолученныеФайлы — независимый непериодический регистр: Клиент, ИдентификаторСообщения, ДатаПолучения, ОригинальноеИмя, РазмерБайт, ОтносительныйПуть (внутри настроенного корня). Хранение на диске, не в БД. Каждая завершённая передача — новая запись и новый файл; блоки одной передачи не создают отдельных записей. Для больших файлов служебный регистр ТЛМ_ЗагрузкиФайлов хранит состояние незавершённых передач (клиент, upload_id, ожидаемый размер, принятый offset, метаданные, статус). Повтор блока/завершения той же загрузки не создаёт дубликатов. Сервер создаёт пути только из своих UUID и даты; оригинальное имя — метаданные, не путь. Не исполнять/распаковывать/публиковать файлы. Временный файл, проверка записи, безопасное перемещение, фиксация регистра; при ошибке очистить временный/свой незафиксированный файл и не отвечать success; документировать reconciliation crash-window и проверку сирот. Никакого уничтожения старых данных.
- Минимальные роли расширения: администрирование отдельно от записи техническим пользователем; штатные ACL/без привилегированного режима. Запрет неавторизованного доступа к истории, хешам и секретам.

Константы:
| Имя | Тип | Значение |
|---|---|---|
| ТЛМ_Сервер_КаталогФайлов | Строка | абсолютный каталог в ОС сервера исполнения, пусто запрещает прием файлов |
| ТЛМ_Сервер_МаксимальныйРазмерJSONМБ | Число | 10 по умолчанию |
Лимита общего размера файла в расширении нет. Лимит JSON положительный, МБ = 1024² байт. Лимит одного HTTP-запроса зависит от инфраструктуры; фиксированный технический размер блока 8 МиБ, без отдельной константы. Клиент читает файл частями, сервер пишет частями на диск. 64-битные размеры и смещения, никакой полной буферизации многогигабайтного файла. Целевая поддержка 2–3 ГиБ и больше; реальный предел подтверждается испытаниями. Настройки по умолчанию должны реально применяться без форм. Не выдавать PASS при неинициализированном хранилище. Каталог вне web root, права на запись только нужному пользователю процесса, никаких жёстких Windows-путей в коде.

## Приёмка v1
1. Установка обоих расширений в чистую тестовую ИБ, без БСП и изменений конфигурации; обновление поверх прошлой версии без потери истории (когда она появится).
2. Передача из неопубликованной ИБ по расписанию и вручную; 2 разных клиента, PowerShell 5.1, Python, cURL; один POST для каждого JSON/обычного файла; многогигабайтный файл через автоматические блоки.
3. JSON с кириллицей, массивом, вложенными данными, пробелами и переносами сохраняется без изменений; параллельные/повторные сообщения не теряются.
4. Двоичный файл, пустой файл, кириллическое имя, одинаковое имя несколько раз, SHA-256 исходного и полученного совпадают.
4а. Обязательная реальная передача 2 и 3 ГиБ с SHA-256, контролем RAM, одновременных загрузок, обрыва, повторного блока и завершения, отсутствия записи до завершения; испытать файл больше 4 ГиБ при доступной среде, отдельно отметить NOT_RUN. Проверить 64-битные смещения, место и таймауты.
5. Отсутствующий/неверный/отозванный токен, превышение лимита, недоступный/переполненный каталог, traversal, сбой БД и обрыв сети: отказ без ложного успеха, без утечки.
6. TLS: доверенный сертификат, импортированный/явный самоподписанный с верным SAN; неизвестный/просроченный/неверный SAN отклоняется; проверить IP и DNS. Токен не передаётся в query, логах, ошибках, redirect.
7. Отдельно записать матрицу реальной проверки платформы, ОС, публикации, файлового/серверного режима и safe mode. Не абстрагировать ограничения доступа к FS/HTTP, документировать настройки безопасности расширения/профиля.
8. Полные XML/BSL ZIP обоих расширений; манифесты, хеши, инструкции, скрипты, тестовый отчёт, README, CHANGELOG и проверенные ссылки. CFE только при фактической штатной сборке. Нативная проверка CheckConfig и E2E отдельно от BSL LS и ZIP.
