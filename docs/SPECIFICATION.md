# Техническое задание v1.0 — 1C-telemetry

Статус поставки и проверок указан в [отчёте приёмки](ACCEPTANCE.md). Цель — простой универсальный транспорт JSON и файлов из любых 1С и скриптов в одну центральную 1С. Заказчик — администратор и разработчик своих задач.

## Границы
Два независимых расширения (назначение «Дополнение»), префикс ТЛМ_, основной язык заимствуется для совместимости с целевой базой. Для работы используются штатные сервисы 1С и веб-сервер. Прикладные объекты относятся к самим расширениям. Никакого анализа бизнес-содержимого JSON, автоматического удаления истории или исполнения файлов. Поддержка конфигураций с управляемым интерфейсом, файловых и клиент-серверных ИБ, Windows/Linux, IIS/Apache, IP/DNS, HTTPS публичного/частного УЦ и самоподписанного сертификата — целевая матрица, не заявление о проверенной совместимости. Минимальная версия и режим совместимости определяются по реальной платформенной проверке, стартовый ориентир 8.3.27.

## Клиент
Общий модуль ТЛМ_Клиент, серверное выполнение (не привилегированный и не глобальный); доступ из пользовательского серверного BSL, включая регламентные задания. Экспортные функции:
- ОтправитьJSON(JSON): готовая строка UTF-8; не преобразовывать структуру, сохранять исходный текст.
- ОтправитьФайл(ПутьКФайлу): файл доступен среде исполнения BSL (в клиент-серверной ИБ это сервер 1С); исходное имя извлекается из пути и кодируется в URL.
- ПроверитьПодключение(): GET ping проверяет TLS и токен, не пишет историю.
Единый контракт результата всех трёх функций определён в [TRANSFER-AND-ERRORS.md](TRANSFER-AND-ERRORS.md): Успех, КодОшибки, ОписаниеОшибки, КодHTTP, Идентификатор, Состояние. Штатные ошибки возвращаются структурой; неизвестный итог отличать от отказа. Один вызов ОтправитьФайл — один POST с исходным файлом целиком. Без скрытых повторов, очередей, заданий, разделения файла, сборки или возобновления передачи. Заказчик самостоятельно подготавливает/разделяет файлы и назначает таймаут.

Константы:
| Имя | Тип | Значение |
|---|---|---|
| ТЛМ_Клиент_АдресСервера | Строка | полный HTTPS URL корня сервиса |
| ТЛМ_Клиент_Токен | Строка | секрет источника |
| ТЛМ_Клиент_ПутьКСертификату | Строка | необязательный путь к публичному PEM на машине исполнения, пусто — системное доверие |
| ТЛМ_Клиент_Таймаут | Число | секунд, по умолчанию 60 |

Не создавать форм констант вручную. Заполнять стандартными средствами (при отсутствии удобного штатного интерфейса — программно через Константы в администраторском BSL). Запрет пустых адреса/токена и переадресации секрета на другой origin. HTTPS обязателен, сертификат и имя/IP проверяются. TLS-ошибку возвращать с понятной диагностикой без секретов.

Заказчик создаёт свой серверный модуль и регламентное задание в собственном расширении. В процедуре самостоятельно формирует произвольный JSON (например из выборки) и вызывает библиотеку. Настройка расписания в Конфигураторе и штатных средствах конкретной конфигурации. Для неопубликованной файловой ИБ нужен работающий исполнитель регламентных заданий; закрытая ИБ сама не запускается. Пример отдельного расширения с регламентным заданием или полный XML/BSL образец без зависимости от конкретной конфигурации; отдельно пояснить запуск в файловой/серверной ИБ.

## Сервер
- ТЛМ_ПриемДанных: единственный HTTP-сервис, RootURL telemetry, POST /json, POST /file, GET /ping. Авторизация по X-Token. HTTPS на веб-сервере, а не внутри расширения.
- ТЛМ_Сервер проверяет токен каждого запроса до приёма данных и определяет активного клиента по точному совпадению. Технический пользователь публикации получает необходимые права на чтение справочника и запись телеметрии.
- ТЛМ_Клиенты — справочник с наименованием, признаком активности и реквизитом `Токен`. Администратор вручную назначает уникальную непустую строку в штатной карточке. Для смены токена редактирует поле, для блокировки снимает признак активности. Карточка сохраняет связь с журналом поступлений.
- ТЛМ_ПолученныеJSON — независимый непериодический регистр сведений: измерения Клиент и ИдентификаторСообщения (UUID в проверенном допустимом типе), реквизит/ресурс ДатаПолучения (UTC по часам сервера), JSON (строка неограниченной длины, проверить платформой). Хранить каждый принятый JSON целиком, включая пробелы, кириллицу и переносы, без десериализации/схемы/извлечения полей. Проверка транспортного UTF-8 и лимита не является разбором JSON. Администратор получает список через штатный отбор по клиенту/дате. Повторная отправка — отдельная запись; две записи в секунду не перезаписывают друг друга.
- ТЛМ_ПолученныеФайлы — независимый непериодический регистр: Клиент, ИдентификаторСообщения, ДатаПолучения, ОригинальноеИмя, РазмерБайт, ОтносительныйПуть (внутри настроенного корня). Хранение на диске, не в БД. Каждый успешно принятый POST — новая запись и новый файл. Сервер формирует имя файла из UUID сообщения; оригинальное имя — метаданные, не путь. Не исполнять/распаковывать/публиковать файлы. Временный файл, проверка записи, безопасное перемещение, фиксация регистра; при ошибке очистить временный/свой незафиксированный файл и не отвечать success; документировать reconciliation crash-window и проверку сирот. Никакого уничтожения старых данных.
- Минимальные роли расширения: администрирование отдельно от записи техническим пользователем; штатные ACL/без привилегированного режима. Запрет неавторизованного доступа к истории, хешам и секретам.

Константы:
| Имя | Тип | Значение |
|---|---|---|
| ТЛМ_Сервер_КаталогФайлов | Строка | абсолютный каталог в ОС сервера исполнения. Пустое значение на Windows использует `C:\temp` с созданием при первой загрузке. На Linux путь задаётся явно |
| ТЛМ_Сервер_МаксимальныйРазмерJSONМБ | Число | 10 по умолчанию |
Лимита общего размера файла в расширении нет. Лимит JSON положительный, МБ = 1024² байт. Лимит одного HTTP-запроса зависит от инфраструктуры. Использовать штатную передачу файла из файла/в файл без лишнего копирования и base64; проверить доступные API и реальный расход памяти платформы. Не вводить искусственный предел Int32 размера. Проверить возможность прямой отправки 2–3 ГиБ, но не гарантировать её до испытаний и не создавать отдельный протокол ради достижения размера. Если инфраструктура не позволяет отправить целый файл, заказчик самостоятельно делит его до вызова. Настройки по умолчанию должны реально применяться без форм. Не выдавать PASS при неинициализированном хранилище. Каталог вне web root, права на запись выдаются пользователю процесса. Явная настройка каталога имеет приоритет над значением по умолчанию.

## Приёмка v1
Порядок стендовых испытаний: [TEST-PLAN.md](TEST-PLAN.md).
1. Установка сервера в имеющуюся тестовую ИБ и отдельная проверка клиента; дополнительно проверка в чистой тестовой ИБ без БСП при доступности, без изменений основной конфигурации; обновление поверх прошлой версии без потери истории (когда она появится).
2. Передача из неопубликованной ИБ по расписанию и вручную; 2 разных клиента, PowerShell 5.1, Python, cURL; один POST для каждого JSON и каждого файла.
3. JSON с кириллицей, массивом, вложенными данными, пробелами и переносами сохраняется без изменений; параллельные/повторные сообщения не теряются.
4. Двоичный файл, пустой файл, кириллическое имя, одинаковое имя несколько раз, SHA-256 исходного и полученного совпадают.
4а. Испытать прямую передачу 2 и 3 ГиБ при доступной среде, сравнить SHA-256 исходного и полученного файла, измерить RAM и время; зафиксировать фактический предел или ошибку и настройки. Если среда не позволяет, описать ограничение/NOT_RUN; не усложнять реализацию разделением файла. Проверка обычной передачи и обработки отказов обязательна.
5. Отсутствующий/неверный/отозванный токен, превышение лимита, недоступный/переполненный каталог, traversal, сбой БД и обрыв сети: отказ без ложного успеха, без утечки.
6. TLS: доверенный сертификат, импортированный/явный самоподписанный с верным SAN; неизвестный/просроченный/неверный SAN отклоняется; проверить IP и DNS. Токен не передаётся в query, логах, ошибках, redirect.
7. Отдельно записать матрицу реальной проверки платформы, ОС, публикации, файлового/серверного режима и safe mode. Не абстрагировать ограничения доступа к FS/HTTP, документировать настройки безопасности расширения/профиля.
8. Полные XML/BSL ZIP обоих расширений; манифесты, хеши, инструкции, скрипты, тестовый отчёт, README, CHANGELOG и проверенные ссылки. Заказчику только исходные ZIP, без CFE. Нативная проверка CheckConfig и E2E отдельно от BSL LS и ZIP.
